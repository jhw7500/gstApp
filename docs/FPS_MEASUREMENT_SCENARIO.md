# 프레임레이트 실측 시나리오

채널 조합별 **실제 전달 fps** 를 재는 재사용 절차. 2026-09-07 세션에서 밟은 함정을
스크립트가 구조적으로 막도록 정리했다.

- 실행 스크립트: `test/run-fps-scenario.sh` (타겟 보드에서 실행)
- 대상 보드 예: `pim-camera-v016` (192.168.214.4)

---

## 0. 한 줄 규칙

> **fps 는 gstApp 을 띄워서 잰다. `media-ctl` + `v4l2-ctl` 로 직접 캡처해서 재면 안 된다.**

raw v4l2 경로는 max9296 **`prepare` sysfs 를 거치지 않는다.** gstApp 은 기동 시 `prepare` 에
(해상도·fps·code·enable·crop) 지문 전체를 써서 디시리얼라이저와 AP1302 모드 테이블을 완전
프로그래밍한다 (`max9296Prepare.cpp:417~`, `main.cpp:931~`). `enable` 을 쓰고 `media-ctl` 로
포맷만 협상하면 링크가 완전 구성되지 않아 **레이트가 20~25% 낮게 나온다.**

같은 조건을 두 경로로 잰 실측 (2026-09-07, 640x360, LED off, `ae_on=false`):

| 조건 | raw v4l2 (`prepare` 미경유) | gstApp (`prepare` 경유) | 차이 |
|---|---|---|---|
| @120 ch0+ch1 | 95.09 | **117.5** | +23.6% |
| @120 ch0+ch2 | 114.2 / 114.3 | **116.8 / 115.1** | +2% |
| @60 ch0+ch1 | 54.04 | **59.87** | +10.8% |

raw v4l2 측정 중 `prepare` 상태는 내내 `IDLE` 이었다. 낮은 값은 물리적으로 그럴듯해서
하드웨어 병목처럼 읽히고, 스스로를 검증해 주지 않는다 — 이 오류로 조명·노출·오라클을
차례로 의심하며 측정 라운드 세 번을 낭비했다.

## 0-1. 두 번째 규칙

> **노출(`exp_time`)을 통제 변수로 명시하지 않은 fps 측정은 무효다.**

AP1302 트리거가 노출 중심(`R0x1186` SYNC_MODE=2)이라 **노출이 fps 를 직접 좌우한다.**
같은 720p@60 4채널 구성에서 노출만 바꾼 실측: 2,000µs → 52.05 / 10,000µs → **59.33** /
16,000µs → 57.35. 게다가 운영 config 는 **버스별로 다른 노출**을 준다(`i2c2=2000`, `i2c1=50000`).
이걸 통제하지 않으면 버스 간 fps 차이가 생기고 그것을 "하드웨어 특성"으로 오독하게 된다 —
실제로 그렇게 오독했다. 스크립트는 `-x/--exp` 로 양 버스에 같은 값을 강제하고 되읽어 검증한다.

**단, 기준 조건의 `ae_on` 은 `true` 다** (드라이버 기본값 `default=1`). 노출을 고정하려고 AE 를
끄는 것은 **기전 규명용 통제 조건**이지 기준 측정 조건이 아니다. 기준 측정은
`--ae true --led false`(스크립트 기본값)로 하고, 노출 의존성을 보려 할 때만 `--ae false -x <us>`
를 쓴다. LED 를 켜고 시험할 때는 `flash_delay` 를 0 으로 둔다(스크립트가 항상 0 으로 쓴다).

**raw v4l2 를 써도 되는 경우는 하나뿐이다:** 드라이버가 어떤 모드를 **열거**하는지 확인할 때.
`VIDIOC_SUBDEV_ENUM_FRAME_INTERVAL` 은 드라이버가 스스로 답하는 값이라 `prepare` 와 무관하다.

## 0-2. 세 번째 규칙

> **듀얼와이드 쌍의 두 채널은 `exp_time` 이 같아야 한다. 갈리면 fps>30 에서 합성이 깨진다.**

ch0/ch1 은 하나의 CSI 로 SERDES GMSL 링크에 묶여 있어 **같은 노출로 돌아야 한다.** 그래서
런타임 변경도 0x11/0x12 에 각각 쓰는 게 아니라 **0x3c 로 양 채널에 한 번에 쓴다.**
AE 관련 값(`ae_on`·`ae_gain`)은 채널별로 써도 된다. `edgeconf_pim.json` 스키마가 이 규칙을
그대로 표현한다 — `exp_time` 은 **버스 레벨**(`i2c2.exp_time`)에만 있고 네 채널 어디에도 없다.

노출 중심 트리거(`R0x1186` SYNC_MODE=2)에서 노출 길이는 곧 프레임 **위상**이다. 쌍의 노출이
갈리면 **두 AP1302 는 모두 119fps 로 정상 생산하는데** 합성 와이드 프레임이 성립하지 않아
CSI2 가 정상의 8~14% 로 떨어지고 ISI 는 0, 앱은 preroll 에 실패한다.

**용량 반응이 있다** (2026-09-08 판별 실험, 640x360 듀얼 120fps, `ae_on` 4채널 false 대칭):

| 쌍의 노출 차 | 결과 |
|---|---|
| 0 (대칭 2000/2000) | 117.4 fps |
| 2,000us (2000/4000) | **46.5 fps** |
| 9,000us (2000/11000) | **16.1 fps** |

**절대값도 프레임주기 초과도 원인이 아니다** — 11000us 를 120fps(주기 8,333us)에서 써도
**양쪽이 같으면 113.9fps 로 정상**이다(2/2). 드라이버가 찍는 `over_period=1` 경고는 이 고장과
무관하다. 되돌리면 재기동 없이 복구된다(109.6 / 114.8).

아래는 **수정 전 max9296 v2.12** 에서 확인한 경로다. `ae_on` 비대칭은 근인이 아니라
**갈림을 만드는 한 경로**였다 — 당시 `max9296.c:2918` 의
`skip_exposure_seed = ae_on && fps > safe_max_fps`(=30) 가 갈리면 노출 시드가 **한쪽에만**
써진다(`:2948` 이 dual 에서 0x11 **또는** 0x12 로 간다). 즉 채널별로 갈려도 되는 값이,
채널별로 갈리면 안 되는 값을 갈라놓는다. 상세와 근거는 §5.8.

이 경로는 max9296 [#64](https://github.com/jhw7500/max9296/issues/64)와
[PR #66](https://github.com/jhw7500/max9296/pull/66)(`7ec2949`, 2026-09-08)에서 쌍 단위
시드 결정으로 수정됐다. 패키지 정본(`edgeconf_pim_base.json`)도 4채널 전부 `ae_on=true` 로
대칭이고 노출이 버스 단위라 수정 전에도 안전했다. 상세한 수정 전후 상태는 §5.8.8에 있다.

## 1. 빠른 사용법

```bash
# 호스트에서 배포
scp test/run-fps-scenario.sh root@192.168.214.4:/root/fpsmeas/

# 1단계: 이 모드가 지원되는지부터 확인 (앱 기동 없음, 1~2분)
ssh root@192.168.214.4 '/root/fpsmeas/run-fps-scenario.sh --res 1280x720 --fps 60 --check-only'

# 2단계: 지원되면 본 측정 (조합당 3회)
ssh root@192.168.214.4 '/root/fpsmeas/run-fps-scenario.sh --res 1280x720 --fps 60 -k "0+1 0+2" -n 3'
```

주요 옵션: `--res WxH` `--fps N` `--combos "0+1 0+2"` `--repeat N` `--duration N` `--check-only`.
전체 목록은 `--help`.

산출물은 `/root/fpsmeas/` 에 `fps_<WxH>@<fps>_<시각>.{log,csv}` 로 남고, 로그 말미에
채널별 평균 요약이 찍힌다.

> ⚠️ 이 측정은 **운영 녹화(`cam-operate.service`)를 정지시킨다.** 스크립트는 trap 으로 어떤
> 종료 경로에서도 설정을 md5 검증하며 되돌리고 서비스를 재기동한다. 그래도 실행 전에
> 보드 점유를 확인할 것.

## 2. 절차 (스크립트가 수행하는 순서)

| # | 단계 | 왜 필요한가 |
|---|---|---|
| 1 | 설정 md5 백업 (`edgeconf.orig.json`) | 어떤 종료 경로에서도 원복하기 위해. 백업은 최초 1회만 만든다 |
| 2 | 자기 명령줄에 앱 이름 리터럴이 있으면 **실행 거부** | killcam 이 그 문자열을 가진 프로세스를 죽인다 |
| 3 | fps 예산 검사 | `채널수 x fps` 가 한도를 넘으면 앱이 기동을 거부한다 (§4) |
| 4 | **모드 지원 여부 확인** (frame interval 열거) | 지원되지 않는 fps 는 거부되는 게 아니라 **조용히 무시**된다 (§4) |
| 5 | `cam-operate` 정지 → `pkill -x killcam` | 노드를 잡고 있으면 측정 불가, 감시자가 시험 앱을 죽인다 |
| 6 | `jq` 로 시험 config 생성 후 **되읽어 검증** | LED off·채널·해상도가 실제로 반영됐는지 확인. 불일치면 회차 폐기 |
| 7 | `cam_hard_reset.sh -q` | 모드 변경은 같은 epoch 안에서 `-ESTALE(116)` 로 거부된다 |
| 8 | 앱을 **다른 이름**(`capapp`)으로 복사해 `-d 5 -m 4 -g 5` 로 기동 | killcam 회피 + NOTICE 를 stdout 으로 |
| 9 | **ISI 인터럽트 증가로 스트림 시작 감지** | 시작까지 13~20초 걸린다. 고정 워밍업을 쓰면 안 된다 (§4) |
| 10 | `prepare` 가 `CONSUMED`/`READY` 인지 확인 | 이게 raw v4l2 와의 결정적 차이. 아니면 값을 신뢰하지 않는다 |
| 11 | 안정화 후 정해진 구간만 인터럽트 델타로 측정 | 램프업이 섞이지 않게 |
| 11b | 측정창 **전후로 앱 pid·경과시간을 비교**, 바뀌었으면 회차 폐기 | 측정 중 앱이 재시작하면 재초기화 구간이 섞여 `ISI=0` 같은 값이 나온다 |
| 12 | 회차 종료: 앱 정지, 녹화 산출물 삭제 | 용량 압박 방지 |
| 13 | 복구: config md5 복원 + hard reset + `cam-operate` 재기동 | trap 으로 무조건 |

### 판정 오라클 3종

| 오라클 | 계산 | 성질 |
|---|---|---|
| **CSI2 인터럽트 ÷ 2** | `/proc/interrupts` 의 `32e50000.csi`(ch0/1), `32e40000.csi`(ch2/3) | 프레임당 Frame Start + Frame End 2회. 해상도 무관. **주 오라클** |
| ISI 인터럽트 | `32e02000.isi`(ch0/1), `32e00000.isi`(ch2/3) | 보통 프레임당 1회지만 **고부하에서 1.37~2.95 로 흔들린 기록**이 있다. 참고값 |
| gstApp `enc-stat` | `chN enc-stat[5s] in=NNN(xx.xfps)` | 앱이 인코더에 넣은 프레임 수 = 최종 전달률. `queue_tune.enc_stat_sec>0` 필요 |

셋이 어긋나면 결론을 내지 말고 원인을 먼저 찾는다.

## 3. 결과 판독법

- **듀얼와이드(한 디시리얼라이저에 2채널, `enable=3`)**: 두 채널이 한 프레임에 나란히 실려
  오므로 그 CSI 의 프레임률이 **두 채널 각각의 fps** 와 같다. 폭은 2배로 전송된다.
- **단일(`enable=1` left / `2` right)**: 그 CSI 의 프레임률이 해당 채널의 fps.
- CSI2 ≫ ISI 이면 ISI 병목, CSI2 가 요청치에 못 미치면 상류(카메라 F/W·AP1302 ISP·SERDES) 한계.

## 4. 함정 (전부 실측으로 확인됨)

| 증상 | 원인 | 조치 |
|---|---|---|
| 값이 20~25% 낮게 나오는데 그럴듯함 | raw v4l2 로 재서 `prepare` 미경유 | **gstApp 으로 측정.** `prepare` 상태가 `CONSUMED/READY` 인지 확인 |
| 요청 60 에 29.85 가 나옴 | 그 fps 가 열거되지 않아 **요청이 무시**되고 기존 fps 로 돎 | 측정 전 `--check-only` 로 열거 확인. 절반이 나온 게 아니다 |
| 모든 값이 일정 비율로 축소, 채널 간 값이 회차마다 **뒤바뀜** | 고정 워밍업이 짧아 측정창에 비스트리밍 구간 포함 | 시작을 **감지**한 뒤 측정창을 연다. 뒤바뀜은 하네스 타이밍 신호 |
| `Unable to setup formats: Invalid argument (22)` (media-ctl) | 그 해상도/fps 조합이 모드 테이블에 없음 | 열거로 확인. 720p@60 은 v2.11 에서 미지원 |
| `Stale file handle (116)` | 같은 hardware epoch 안에서 지문 변경 | 케이스마다 `cam_hard_reset.sh -q` 선행 |
| 해상도가 v4l2 열거에서 사라짐 → `EINVAL` | hard reset 이 `enable` 을 0 으로 만듦 | 리셋 후 `enable` 을 다시 쓴다 (raw v4l2 경로에 한함) |
| 시험 프로세스가 갑자기 SIGKILL | 명령줄에 앱 이름 리터럴 → killcam | 다른 이름으로 복사해 실행. 스크립트가 자기 명령줄을 사전 검사한다 |
| 앱이 기동 직후 종료 | `채널수 x fps` 가 fps 예산 초과 | 360p/720p=240, 1080p=180 (`max9296Controls.cpp:73`). `dual_enc=TRUE` 면 2배로 계산됨 |
| 측정마다 값이 크게 흔들림 | AE 가 조명에 따라 노출을 프레임주기까지 밀어붙임 | `ae_on=false` 로 고정 (스크립트 기본값) |
| **버스(CSI0/CSI1)별로 fps 가 5~6 갈림** | **운영 config 가 버스별 노출을 다르게 준다** (`i2c2.exp_time=2000`, `i2c1.exp_time=50000`). 이걸 통제 안 하면 "버스/하드웨어 특성"으로 오독한다 — 실제로 오독했다 | `-x/--exp` 로 **양 버스에 같은 값 강제**. 스크립트가 되읽어 검증하고 불일치면 회차 폐기 |
| 노출을 늘렸는데 fps 가 **올라감**(반직관) | AP1302 트리거가 **노출 중심**(`R0x1186` SYNC_MODE=2)이라 노출 길이가 프레임 타이밍을 좌우 | 이상 아님. 노출을 통제 변수로 명시하고 값을 함께 기록한다 |
| 운영 config 를 확인 안 하고 시험 config 를 만듦 | 시험이 운영과도 다르고 통제도 안 된 어중간한 상태가 된다 | 시험 config 는 **운영 파일에서 `jq` 로 파생**하고, 바꾼 필드를 로그에 전부 남긴다 |
| `ISI=0` 인데 CSI2 는 조금씩 늘어남, 그런데 녹화 파일은 정상 생성됨 | 측정창이 **앱 재시작/재초기화 구간**에 걸침 (설정 변경, 감시자 재기동 등) | 측정창 전후로 앱 pid·경과시간을 비교해 폐기. 고장으로 단정하기 전에 `ps -o etimes` 를 먼저 본다 |
| `pkill -f <패턴>` 이 원격 셸을 같이 죽임 | 패턴이 자기 명령줄에 있음 | 브래킷 트릭: `pkill -f 'run-fps-scenari[o]'` |
| 완료 폴링이 오탐 | `grep -c` 는 0건에도 "0"을 출력하고 exit 1 → `\|\| echo 0` 이 겹쳐 출력 | `grep -q` 로 판정하고 단일 토큰을 출력 |
| **듀얼와이드에서 AP1302 는 양쪽 119fps 인데 CSI2 가 정상의 8~14%, ISI 가 0** | **쌍의 노출이 갈림**(`exp_time` 은 i2c 라인 공유값이다). `ae_on` 비대칭이 시드를 한쪽에만 쓰게 만드는 것이 흔한 경로 | 노출은 0x3c 로 양 채널 동시에. 차이가 클수록 더 무너진다(2,000us→46fps, 9,000us→16fps). §0-2·§5.8 |
| 채널이 "N초 뒤에 죽는다"는 시각이 안 맞음 | 측정 스크립트의 **샘플링 오프셋**(워밍업 `sleep`)이 로그에 없음 | 오프셋을 반드시 기록하고 t=0 을 캡처 기동 시점으로 잡는다. 이 누락이 오진을 낳았다(§5.8.5) |

| 시험을 Ctrl-C 로 끊었더니 **운영 config 가 시험값(또는 잘린 JSON)으로 남음** | 복원 여부를 정하는 플래그를 config 쓰기 **뒤**에 세움. Ctrl-C 는 포그라운드 그룹 전체에 SIGINT 를 보내므로 `cp` 자신이 쓰기 도중 죽는다 | 플래그를 쓰기 **앞**에 세운다. `test/run-probe-safety-source-check.sh` 가 이 순서를 검사한다 |

| 분산 ch0+ch2 | 운영값 그대로 | ch0 50.35 | ch2 56.77 |
| **4채널 듀얼와이드** | **양 버스 exp=2000 통일** | **52.05** | **52.05** |
| **4채널 듀얼와이드** | **양 버스 exp=16000 통일** | **57.35** | **57.08** |

**핵심: 버스 간 차이는 하드웨어가 아니라 노출 설정 차이였다.** 노출을 통일하면 두 버스가
0.3fps 안에서 일치한다. 그리고 노출을 2ms→16ms 로 늘리면 **양쪽 다 52 → 57 로 오른다**(반직관).

계층별 측정(`cam_fps_stack.sh`)으로 손실 지점도 특정됐다 — **센서→ISP 구간**이다.
센서(AR0234)는 양 버스 모두 59.7~60.0 을 공급하고(레지스터상 이론값 61.1~61.4),
ISP→CSI2→ISI 는 ±1% 로 손실이 없다. 노출이 짧은 쪽에서 AP1302 가 프레임을 더 버린다.

**기전과 이미 알려진 손잡이** (원본: `max9296` 저장소 `docs/fps-limit-analysis.md`, 2026-08-11):
- `R0x1186` TRIGGER_CTRL = `0x008a` (MODE 2, **SYNC_MODE 2 = 노출 중심 트리거**) — 이번 실측에서도
  4개 AP1302 전부 `008a` 로 동일. 트리거가 노출 기준이라 **노출 길이가 fps 를 좌우**한다.
- `R0x6112` TRIGGER_MAX_MISMATCH = 기본 `20`µs (이번 실측 `0x0014` = 20, 4개 모두 동일).
  같은 문서 실측: **`0` 으로 두면 FHD@60 이 19.8 → 26.7, HD@50 이 46.0 → 49.8 로 개선**된다.
  **gstApp 은 이 레지스터를 건드리지 않는다**(저장소 전체에 `1186`·`6112` 문자열 없음).

**같은 문서의 선행 실측** (조건: 펌웨어 기본값, 레지스터 조작 없음 = AE auto, `exp_time=10000`):
- FHD 1920x1080: 40 요청 → 19.89, 50 → 21.82, 60 → 19.84. **정수 트리거 분주**이며 30 보다 나쁘다.
- HD 1280x720 @60: **54.03 ~ 55.5 fps**. (60 근처가 아니다. 59.87 은 360p@60 값이다.)

### 5.3 결론 — HD60 은 달성된다. 손잡이는 `exp_time` 이다 (2026-09-07)

같은 스트림 위에서 레지스터만 바꾼 A/B/C/A' 대조 (720p@60, 4채널, 양 버스 `exp_time=10000`):

| 단계 | 설정 | CSI0 | CSI1 |
|---|---|---|---|
| A | 기본값 (`6112=0x0014`, `2020=0x1e00`) | **59.33** | **59.33** |
| B | `R0x6112 = 0` | 59.07 | 59.04 |
| C | `R0x6112 = 0` + `R0x2020 = 0x3C00` | 59.10 | 59.10 |
| A' | 기본값 복원 (가역성 확인) | 59.12 | 59.09 |

**`R0x6112=0` 은 이 동작점에서 효과가 없다** (네 단계가 0.29fps 안에 든다). 이 레지스터는 프레임
스킵을 억제하는 손잡이인데 이미 요청의 98.9% 가 나오고 있어 회수할 프레임이 없다. 선행 문서의
개선 사례(FHD@60 19.8→26.7, HD@50 46.0→49.8)는 **스킵이 심한 영역**에서 잰 값이다.
`R0x2020`(MAX_FPS) 무효도 선행 문서의 "단독으로는 효과 없음" 기록과 일치한다.

**진짜 손잡이는 노출이다.** 같은 4채널 720p@60 구성에서 노출만 바꾼 값:

| 양 버스 `exp_time` | 채널당 fps | 요청 대비 |
|---|---|---|
| 2,000 µs | 52.05 | 87% |
| **10,000 µs** | **59.33** | **98.9%** |
| 16,000 µs | 57.35 | 96% |

**1280x720@60 은 v2.12 + HD60 앱에서 4채널 동시에 채널당 59.1~59.3fps 로 달성된다**
(total_fps 240 = 예산 상한). 하드웨어 개조도 레지스터 패치도 필요 없고, config 의 노출값만
맞추면 된다. 운영 config 의 `i2c2.exp_time=2000` 이 CSI0 를 52 로 끌어내리고 있었다.

> ⚠️ 노출은 **화질(밝기·모션블러)과 직결**된다. fps 만 보고 정할 값이 아니며, 현재 값이 의도적
> 선택일 수 있다. 위 표는 fps 관점의 측정 결과일 뿐이다.

앱을 한 번만 띄우고 **같은 스트림 위에서** v4l2 컨트롤(`exp_time_ch0..ch3`)로 노출만 바꿔 잰
값. 4채널 720p@60, LED off, `ae_on=false`. 각 점 15초. 리드백은 전 구간 요청값과 일치.

| `exp_time` (µs) | CSI0 | CSI1 | 요청 60 대비 |
|---|---|---|---|
| 2,000 | 51.30 | 51.23 | 85% ← **운영 `i2c2` 현재값** |
| 4,000 | 52.70 | 53.77 | 88% |
| 6,000 | 56.37 | 56.40 | 94% |
| 8,000 | 58.77 | 58.80 | 98% |
| 9,000 | 58.90 | 58.84 | 98% |
| 10,000 | 59.00 | 59.00 | 98% |
| **11,000** | **59.27** | **59.24** | **99%** ← 정점 |
| 12,000 | 59.02 | 59.02 | 98% |
| 14,000 | 58.75 | 58.75 | 98% |
| 16,000 | 56.60 | 56.70 | 94% |
| 18,000 | 55.77 | 55.97 | 93% |

**뒤집힌 U 곡선이다.** 정점은 **11,000µs(59.27fps, 요청의 99%)**, 실용 평탄구간은
**8,000~14,000µs(58.7~59.3fps, 98% 이상)**. 그 아래위로 급격히 떨어진다:
- 6,000 이하 → 56 이하. 2,000(운영 `i2c2` 값)에서는 **51.3(85%)** 까지 내려간다.
- 16,000 이상 → 56 대로 하락. 노출이 프레임주기(16.67ms)에 근접·초과하면서 나타난다.

두 버스가 전 구간에서 0.1~1.1fps 안에 붙는다 — **노출을 맞추면 버스 차이는 없다**는 §5.3
결론이 11개 점에서 재확인된다.

**운영 관점 권고(주의사항 포함):** 720p@60 을 쓸 경우 `exp_time` 을 **8,000~12,000µs** 로 두면
채널당 58.8~59.3fps 를 얻는다. 현재 `i2c2.exp_time=2000` 은 51.3fps 로, 요청의 85% 다.
다만 **노출은 화질(밝기·모션블러)과 직결**되므로 fps 만 보고 정할 값이 아니고, 현재 값이
의도적 선택일 수 있다. 위 표는 fps 관점의 측정 결과일 뿐이다.

원본: 타겟 `/root/fpsmeas/sweep_20260907_042838.csv`

### 5.5 왜 노출이 짧으면 fps 가 주는가 — 위치는 확정, 기전은 미규명

노출별로 AP1302 의 센서 타이밍 레지스터와 실측 fps 를 **같은 스트림에서** 나란히 읽었다
(720p@60 4채널). 센서 fps 는 `R0x00FC` SENSOR_TOTAL_FRAME_TIME 의 역수다.

| 노출 µs | 센서 총프레임 µs (ch0/ch2) | 센서 fps | 실측 fps | **ISP 폐기율** | `R0x0006` ERROR |
|---|---|---|---|---|---|
| 2,000 | 16,843 / 16,704 | 59.37 / 59.87 | 51.69 / 51.65 | **12.9% / 13.7%** | `0000` |
| 4,000 | 16,873 / 16,707 | 59.27 / 59.86 | 52.75 / 53.37 | 11.0% / 10.8% | `0000` |
| 8,000 | 16,976 / 16,896 | 58.91 / 59.19 | 58.97 / 58.97 | **≈0%** | `0000` |
| 11,000 | 16,757 / 17,108 | 59.68 / 58.45 | 59.48 / 59.48 | ≈0% | `0000` |
| 16,000 | **17,574** / 16,748 | **56.90** / 59.71 | 57.61 / 57.57 | ≈0% / 3.6% | `0000` |

**확정된 것:**
1. **센서 타이밍은 노출과 무관하게 고정이다.** 라인시간 11.87µs, 프레임시간 12,816µs 가 전 구간
   동일하고 총프레임시간도 16.7~17.0ms(≈59fps)를 유지한다. AP1302 가 센서를 느리게
   재프로그래밍하는 것이 **아니다**.
2. **짧은 노출에서 AP1302 ISP 출력단이 프레임을 버린다** — 2,000µs 에서 13%, 4,000 에서 11%,
   8,000 이상에서 0%. `ERROR` 는 전 구간 `0x0000` 으로 **아무것도 보고하지 않는다**(조용한 폐기).
3. **곡선 오른쪽은 기전이 다르다.** exp=16,000 의 ch0 은 총프레임시간이 17,574µs 로 늘어 센서
   자체가 56.90fps 로 느려졌다 — 노출이 프레임주기(16.67ms)에 육박한 고전적 한계다.
   즉 **U 곡선의 양쪽은 서로 다른 원인**이다.

**기각된 가설 (전부 실측):**

| 가설 | 검증 | 결과 |
|---|---|---|
| 트리거 어긋남 폐기 (`R0x6112` TRIGGER_MAX_MISMATCH) | exp=2000 에서 0 으로 설정 | **기각** — 51.75 vs 기준 52.6 |
| 어두운·노이즈 영상의 ISP 처리 부하 | exp=2000 에서 게인 8배(256→2048) | **기각** — 52.59 vs 기준 52.6 |
| AP1302 의 센서 프레임길이 재프로그래밍 | 노출별 타이밍 레지스터 | **기각** — 전 구간 고정 |

가역성도 확인했다(기본값 복귀 시 51.61 로 회귀). **ISP 내부에서 무엇이 폐기를 유발하는지는
미규명이다.** 접근 가능한 레지스터로는 더 좁히지 못했고, 진전하려면 AP1302 펌웨어 내부 동작
문서나 벤더 지원이 필요해 보인다. **회피 방법(노출 8,000~12,000µs)은 확정적이고 재현된다.**

원본: 타겟 `/root/fpsmeas/sensortiming_20260907_044836.csv`, `whyexp_20260907_044042.csv`

**아직 측정하지 않은 것**: 720p@60 에서 ISI IRQ 가 프레임당 최대 23회까지 튀는 현상(프레임 수는
정상이라 영상 손실은 아니다). FHD 는 v2.12 에서도 30 이 상한이라 `R0x6112=0` 의 FHD 개선
(19.8→26.7)은 재확인하지 못했다. 노출 변경이 **화질에 미치는 영향**도 측정하지 않았다.

### 5.6 기준 조건 결과 — `ae_on=true`, LED off (2026-09-07)

회차 폐기 0, 설정은 매 회차 config 되읽기로 검증.

| 구성 | 채널 | CSI2 3회 | 평균 | enc-stat | 요청 60 대비 |
|---|---|---|---|---|---|
| **ch0+ch1** | ch0/ch1 | 59.70, 59.63, 59.28 | **59.54** | 59.4~59.8 | **99.2%** |
| **4채널** | ch0/ch1 | 59.40, 59.08, 59.42 | **59.30** | 59.2~59.8 | 98.8% |
| | ch2/ch3 | 59.33, 59.27, 59.40 | **59.33** | 59.4~59.8 | 98.9% |

- **HD 1280x720@60 은 기본 조건에서 채널당 59.3~59.5fps 로 달성된다.** 4채널 동시

- 원본: 타겟 `/root/fpsmeas/fps_1280x720@60_20260907_050146.csv`

### 5.7 360p@120 토폴로지 — **차이를 주장할 근거 없음** (2026-09-07, 정정됨)

> ⚠️ **이 절의 초판은 "CSI 2개 분산이 9% 빠르다"고 결론했다. 그 결론은 철회됐다.**
> 노출을 통제하지 않은 비교였고, 방향도 재측정에서 뒤집혔다.

**철회 경위.** 처음 `ae_on=true` 로 재서 ch0+ch1 107.80 vs ch0+ch2 117.53 (+9%) 을 보고했다.
그러나 예전 측정(v7, `ae_on=false`, exp 2000)에서는 ch0+ch1 이 **117.5** 였다 — ch0+ch2 는 두
조건 모두 ~116 으로 같은데 ch0+ch1 만 AE 를 켜면 10fps 떨어진다. 즉 그 9% 는 토폴로지가
아니라 **AE 가 두 구성에서 다른 노출을 고른 결과**였다.

**노출을 통제한 재측정** (`ae_on=false`, exp 2000 양 버스, `enc-stat` 게이트 적용):

| 구성 | AE off + exp 2000 | v7 (같은 조건) | AE on |
|---|---|---|---|
| `ch0+ch1` (CSI 1개) | **115.64** (117.69·116.47·112.77) | 117.5 | 107.80 |
| `ch0+ch2` (CSI 2개) | **112.36** (유효 1회) | 116.8 / 115.1 | 117.53 |

**노출을 맞추면 두 구성이 비슷하고 오히려 ch0+ch1 이 소폭 높다** — 초판 결론과 방향이 반대다.
다만 ch0+ch2 는 3회 중 2회가 기동 실패로 폐기돼 **유효 표본이 1개뿐**이다.
따라서 정확한 서술은 **"현재 데이터로는 토폴로지 간 유의한 차이를 주장할 근거가 없다"** 이다.
"어느 쪽이 빠르다"고 쓰지 말 것.

### 5.7.1 360p@120 의 간헐적 기동 실패 (재현됨, 원인 미규명)

`ch0+ch2` 조합에서 앱이 프레임을 전혀 받지 못하는 기동 실패가 **2026-09-07 하루에 4회** 관측됐다.

| 실행 | 증상 |
|---|---|
| v7 (02:33) | ch0+ch2 1회차, ch0 미기동 (`enc-stat` 6.4 → 0.0fps) |
| topo-sweep (05:47) | ch0+ch1·ch0+ch2 두 케이스 모두 `NO DATA` |
| 본 측정 (05:56) | **ch0+ch2 3회 중 2회** `NO DATA` (csi1 또는 양쪽) |

같은 실행에서 `ch0+ch1` 은 3회 모두 성공했으므로 **CSI1 을 함께 켜는 구성에 몰려 있다.**
앱 로그: `chN NO DATA for Ns - zero frames reached enc-queue (csiN source not delivering).
This channel's sink cannot preroll, which stalls the whole pipeline in PAUSED`.
`prepare` 는 `CONSUMED ... errno=0` 으로 정상인데 파이프라인만 PAUSED 에 걸린다.
**fps 이전에 안정성 문제이며 실운용 관점에서 더 중요할 수 있다. 원인 미규명.**

> **2026-09-07 추가**: 이 절의 기동 실패 중 `ae_on` 비대칭으로 설명되는 부분은 §5.8 에서
> 규명됐다. 그러나 **정상 fps 로 돌다가 갑자기 전 계층이 멈추는 "동결"은 여전히 별개
> 미규명 현상**이다 — §5.8.6 참조.

### 5.7.2 측정 방법 교훈 — CSI2 만으로는 파이프라인 정지를 못 가린다

`enc-stat` 게이트를 넣기 전 실행에서 **CSI2 가 111.9fps 를 찍는 동안 앱은 `NO DATA`,
`enc-stat in=0`** 이었다. CSI2 카운터는 **디시리얼라이저가 SoC 로 보낸** 프레임을 세므로,
파이프라인이 PAUSED 로 막혀 앱이 한 장도 못 받아도 링크가 살아 있으면 계속 올라간다.
지금까지는 두 값이 늘 일치해서 문제가 드러나지 않았을 뿐이다.
=> 스크립트는 이제 `NO DATA` 문자열과 `enc-stat < 1.0` 을 검사해 **회차를 폐기**한다
(실측에서 실제로 2회차를 걸러냈다).

또 하나: **360p@120 에서는 스트리밍 중 v4l2 로 노출을 바꾸면 파이프라인이 죽는다.**
720p@60 에서는 같은 방식이 11점 내내 정상이었다. 120fps 의 노출 스윕은 **config 에 넣고
케이스마다 재기동**해야 한다.

원본: 타겟 `/root/fpsmeas/fps_640x360@120_20260907_055605.csv`(정정 측정),
`fps_640x360@120_20260907_053036.csv`(초판, AE on), `toposweep_20260907_054657.csv`(무효)

### 5.8 360p@120 듀얼와이드 실패 — **근인: 쌍의 노출 갈림** (2026-09-08 재정정·해소)

> **이 절은 두 번 개정됐다.** 1차(2026-09-07)에서 "듀얼와이드 × 120fps 조합이 원인",
> "ch0+ch1 금지, ch0+ch2 권장", "기동 10~12초 뒤 ch0 가 죽는다"를 폐기했다(근거 §5.8.5).
> 2차(2026-09-08)에서 그때 세운 **"`ae_on` 비대칭이 근인"·"시드 스킵의 200ms 스큐가 기전"도
> 폐기한다** — 근거는 §5.8.8. 아래 본문의 실측 수치는 유효하나 **인과 해석이 바뀌었다.**

**근인**: 듀얼와이드 쌍의 두 채널 **노출이 갈리는 것**. ch0/ch1 은 하나의 CSI 로 SERDES GMSL
링크에 묶여 있어 같은 `exp_time` 으로 돌아야 하고(§0-2), 갈리면 노출 중심 트리거
(`R0x1186` SYNC_MODE=2) 아래서 프레임 **위상**이 어긋나 합성 와이드 프레임이 성립하지 않는다.
**두 AP1302 는 모두 119fps 로 정상 생산한다** — 깨지는 것은 fps 가 아니라 위상이다.

이 절의 고장 수치와 코드 위치는 **수정 전 max9296 v2.12** 기준이다. 원인은 max9296 #64로
추적했고 PR #66(`7ec2949`)에서 수정됐다. 수정 후 상태와 별개 동결 이슈는 §5.8.8 끝에 구분한다.

`ae_on` 비대칭은 근인이 아니라 **갈림을 만드는 흔한 경로**다: `skip_exposure_seed`(`:2918`)가
갈리면 노출 시드가 한쪽에만 써진다(`:2948` 이 dual 에서 0x11 **또는** 0x12 로 간다).
아래 §5.8.2~5.8.4 의 `ae_on` 실측은 그 경로를 통해 노출이 갈린 결과로 읽어야 한다.

**토폴로지도 fps 도 원인이 아니다** — 30fps 를 넘길 때만 드러나는 **설정 문제**다.

#### 5.8.1 파손 지점 — ISI 가 아니라 그 상류

같은 채널·같은 fps·같은 하드웨어에서 json 만 바꿔 잰 값 (t=18s, 1초 간격 샘플):

| config | AP1302 dHINF (ch0/ch1) | CSI2 IRQ/s | ISI IRQ/s | 앱 |
|---|---|---|---|---|
| 현장수정본 (`ae_on` 비대칭) | **107 / 93** (정상 생산) | **24 (=12fps)** | **0** | **0** |
| 통제본 (`ae_on` 대칭) | 117 / 118 | 233 (=116fps) | 117 | 114 |

대조군에서 `CSI2 = ISI × 2` 가 정확히 성립해(232 vs 117) "프레임당 FS+FE 2회" 가정이 실측
검증됐다. 실패 케이스는 이 비례가 완전히 깨지고 **ISI 가 프레임 시작을 한 번도 못 본다.**

#### 5.8.2 단일요인 분해 (통제 시행 21회, `ae_on` 외 전 항목 4채널 통일·회차마다 `unique=1` 검증)

`ch0+ch1` 듀얼와이드 640x360@120, 35초 창, 교차 배치 (`aeon_20260907_081557`):

| 갈래 | ch0/ch1 `ae_on` | 회차별 fps | 평균 | 판정 |
|---|---|---|---|---|
| D1 통제 | `false / false` | 59.8* · 105.2 · 112.0 | 92.3 | 정상 |
| **D2 통제** | **`false / true`** | **10.1 · 11.3 · 9.4** | **10.3** | **3/3 고장** |
| D3 통제 | `true / true` | 98.4 · 100.8 · 103.6 | 100.9 | 정상 |
| D4 **운영값 유지** | `false / false` | 112.7 · 113.0 · 109.2 | 111.6 | 정상 |

<sub>*D1 1회차는 17초에 동결해 표본 구간이 2초뿐. 동결은 별개 현상(§5.8.6).</sub>

- **값이 아니라 비대칭이 문제다.** 둘 다 `false` 정상, 둘 다 `true` 정상, **하나만 `true` 고장.**
- **나머지 6항목은 무죄.** D4 는 `ae_gain` 512/256, `bps` 8192/4096, `awb` auto/d65, `hflip`,
  `wiper`, `flash_delay` 를 **운영값 그대로** 두고 `ae_on` 만 대칭화했는데 111.6fps 로 가장 좋다.

`ch2+ch3` 듀얼와이드 (`ch23_20260907_083448`):

| 갈래 | ch2/ch3 `ae_on` | `exp_time` | 평균 fps | 판정 |
|---|---|---|---|---|
| E1 | `false / false` | 2000 | 112.4 | 정상 |
| **E2** | **`true / false`** | **2000** | **10.8** | **3/3 고장** |
| E3 | `true / false` | **50000** | 103.8 | 정상 |

- **E2 로 비대칭 법칙이 디시리얼라이저와 무관함이 확인됐다** — 두 인스턴스 합쳐 **6/6 고장**.
- **E3 가 반례를 설명한다.** 통제 전 실행에서 `ch2+ch3@120` 이 105fps 로 멀쩡했던 것은
  `i2c1.exp_time=50000` 덕분이다. **비대칭의 해로움은 두 채널의 실효 노출 차이 크기에 달렸다.**

#### 5.8.3 수정 전 v2.12 기전 (소스 확인)

```c
// max9296.c:2918
bool skip_exposure_seed = ch_ctrl->ae_on && fps > safe_max_fps;
```

`MAX9296_EXPOSURE_SAFE_MAX_FPS = 30` (`max9296.c:59`), 1280x360·640x360 모드가 모두 이 값을
쓴다(`max9296.c:919, :929`).

```
fps > 30 ─▶ skip_exposure_seed 판단이 채널마다 갈린다
             ├ ae_on=true  채널: 시드 건너뜀 → AE 자율
             └ ae_on=false 채널: 시드 적용 (exp_time)
                    ↓ 두 채널 실효 노출이 벌어짐 (R0x1186 SYNC_MODE=2 = 노출 중심 트리거)
             듀얼 쌍 ISP 프레임 타이밍 불일치 → 합성 와이드 프레임 미성립
                    ↓
             CSI2 정상의 8~10%(에러성), ISI 0, 앱 preroll 실패 → 파이프라인 PAUSED
```

듀얼 결합 구조 자체는 유효하다 — 시리얼라이저가 두 채널을 한 프레임으로 합쳐 보내므로
한쪽 타이밍이 어긋나면 합성이 성립하지 않는다:

```
ch0 ISP ─┐
         ├─→ 시리얼라이저 합성 → GMSL2 → CSI2 → ISI → 앱
ch1 ISP ─┘
```

**`fps=30` 에서는 `30 > 30` 이 거짓이라 `ae_on` 과 무관하게 양 채널 모두 시드를 받는다(대칭).**
그래서 운영(30fps)은 멀쩡했고, 120fps 에서만 터져 "듀얼와이드 × 120fps 조합"처럼 보였다.

> 이 수정 전 기전은 max9296 이슈 [#64](https://github.com/jhw7500/max9296/issues/64)로 추적했고,
> [PR #66](https://github.com/jhw7500/max9296/pull/66)에서 해결했다. 최종 처방은 단순 경고가 아니라
> 시드의 게이트·값·주소를 모두 듀얼 쌍 단위로 결정하는 것이다(상세 §5.8.8).

#### 5.8.4 패키지 정본은 안전하다 (검증됨)

배포 사슬: `dist/pim/opt/pim/config/edgeconf_pim_base.json` → `/etc/defaultconf.json` →
`/root/shared_v/edgeconf_pim.json` (`pim-package-jhw` `dist/pim/DEBIAN/postinst:391,404`,
`factory_init_pim_gate.sh:19`). 기본 운영 설정은 **정본 + `enc="h265"`** 다(정본 `enc=null`).

정본은 **4채널 전부 `ae_on=true`, `ae_gain=256`, `bps=2048`, 양 버스 `exp_time=10000`** 으로
대칭이고, `exp_time` 이 120fps 프레임주기(8,333us)를 넘어 E3 와 같은 안전 영역이다.

실측 (`dflt_20260907_085621`, 90초 창, 정본에서 바꾼 것은 `enc`·`fps`·`enable`·로그 설정뿐):

| 회차 | 결과 | fps |

> **운용 규칙**: **듀얼와이드 쌍(ch0·ch1 / ch2·ch3)의 `ae_on` 은 같은 값이어야 한다.**
> 30fps 이하에서는 무해하지만 **30fps 를 넘기는 순간 듀얼와이드가 깨진다.**

#### 5.8.6 "동결" — 별개 현상, 조사 진행됨 (근인 미규명)

`ae_on` 비대칭과 무관하게, 정상 fps 로 돌던 스트림이 갑자기 멈추는 현상이 남아 있다.
2026-09-07 오후에 **총 60 회차(각 창 90s)** 를 돌려 아래까지 좁혔다.

##### 무엇이 일어나는가 (시계열 관측, `poll_20260907_120018_slow_t7`)

100ms 해상도로 전환 순간을 잡았다:

```
t=50.0~53.6s   csi_d=24/100ms(=120fps)   A=8,329~8,424us  B=8,341~8,423us   정상
t=53.68s       csi_d=9                   (한 창 안에서 끊김)
t=53.78s       csi_d=0                   CSI 출력 정지
t=53.98s                                 A=7,704   B=9,513
t=54.98s                                 A=9,896   B=9,513
t=55.98s                                 A=8,417   B=9,513
t=56.98s                                 A=8,167   B=9,513
```

**동결 후에도 A 채널은 계속 갱신되고 B 채널만 9,513us 에 고정된다.** 즉 순서는

1. 듀얼 쌍의 **한 채널** ISP 가 멈추고 `R0x00FC` 가 고정된다
2. 살아 있는 채널은 계속 프레임을 만든다(소비자가 없어 이탈 폭이 커진다)
3. 합성 와이드 프레임이 성립하지 않아 **CSI 출력이 100ms 이내에 완전히 끊긴다**

이전 판의 "양쪽 다 9,57us 로 간다"는 정적 스냅샷의 한계였다. 시계열로 보면 한쪽만 죽는다.

##### 정상 동작 중에도 같은 이탈이 일상적으로 일어난다

50Hz(20ms) 샘플링 8 회차에서 **8/8 재현** (`fast_20260907_113226`, 각 t>30s 구간 n=3,000):

| A_total 구간 | 비율 |
|---|---|
| 8,800us 미만 (정상, ≈119fps) | 98.7% |
| 8,800~9,800 (**104fps 대 = 동결 착지값**) | 0.4% |
| 9,800~12,000 | 0.5% |
| 12,000 이상 (**63fps 대**) | 0.3% |

이탈 사건은 **양 채널 모두** 분당 30~50 회 일어나고 **35 회 중 33 회가 1 샘플(20ms) 안에 복귀**한다
(최장 3 샘플=60ms). 이탈 정점은 15,400~18,000us. 평균은 8,388us(σ=383) 로 안정적이라
**1 초 간격 측정으로는 이 이탈이 전혀 보이지 않는다.**

=> 유력한 모형: **동결은 이 일상적 이탈에서 복귀하지 못한 경우다.** 착지값 104.x / 60~61fps 가
   이탈 레벨과 일치하고, 발생 시각이 11~87s 로 무작위인 것도 확률적 복귀 실패로 설명된다.
   거칠게는 이탈 약 200 회당 1 회가 복귀에 실패하는 셈이다.
   **다만 이는 아직 정황이다** — 이탈의 존재·빈도·복귀시간은 8/8 확정이지만, 동결 순간이
   그 이탈의 연장인지는 20ms 해상도로 본 적이 없다(아래).

##### 배제된 것 (BEGIN/FREEZE/END 레지스터 덤프 다수)

GMSL2 링크 단절(`CTRL3` LOCKED=1, `link_a_up`/`link_b_up` true) · AP1302 에러 보고
(`R0x0006`=0x0000) · 커널 인지(기동 이후 dmesg 0건) · 트리거 설정(`R0x1186`·`R0x2020`·
`R0x5440`·`R0x6112` 전부 불변) · 라인시간(`R0x00D8`) · **유효 프레임시간(`R0x00E0`=7,344us
= 라인 6.8us x 정확히 1,080 라인) 불변** — 늘어나는 것은 블랭킹뿐이다 ·
CSI 출력 설정(`0x0313` bit2 는 출력 중 세워지는 상태 비트라 동결 지표가 아니다).

`R0x6112` TRIGGER_MAX_MISMATCH 는 드라이버가 **쓰지 않는다**(`max9296.c:96` 매크로 정의뿐,
전수 확인). 운영 0x0014 / 시험 0x0000 차이는 요청 fps(30 vs 120)에 따른 펌웨어 값이다.

##### 노출 의존성 — 확인되지 않음

노출만 바꾼 통제 시험 15 회 (`frzexp_20260907_105006`, ch2+ch3 듀얼와이드 120fps):

| exp_time | 완주 | 고장 |
|---|---|---|
| 2,000 | 4 | 동결 1 |
| 5,000 | 4 | 기동실패 1 |
| 10,000 | 5 | 0 |

**세 갈래가 구분되지 않는다.** 정본 조건(exp=10,000)의 0/7 을 노출 덕으로 본 초기 추정은
지지되지 않는다 — 그 회차는 채널·bps 등도 함께 달랐다. 없다고 증명된 것도 아니다.

##### i2c 폴링 빈도 의존성 — 미확정

루프·IRQ 접근·판정 로직을 모두 동일하게 두고 **i2c 트랜잭션 수만 50배** 달리한 A/B 20 회
(`poll_20260907_120018`):

| 갈래 | 완주 | 동결 | 기동실패 |
|---|---|---|---|
| slow (i2c 1초) | 8 | 1 | 1 |
| fast (i2c 20ms) | 10 | 0 | 0 |

2/10 vs 0/10 은 Fisher 단측 p≈0.24 로 유의하지 않다. 오늘 누적 slow 계열 5/21 vs
fast 계열 0/18 도 p≈0.06 로 경계선이다 — **시사적이나 미확정**. 다만 실무적으로
**fast 갈래 18 회 연속 무동결**이라 고속 폴링으로 전환을 잡으려는 전략은 성공률이 낮다.

##### 남은 공백

동결 직전 정상 판독과 다음 판독 사이 **1 초가 미해상**이다. B 가 8,341 -> 9,513us 로
점진적으로 갔는지 한 프레임 만에 뛰었는지 아직 모른다. 20ms 로 그 구간을 보려면 fast 갈래에서
동결이 나야 하는데 18 회 연속 나지 않았다.

접근 가능한 레지스터는 전부 확인했고 에러도 커널 로그도 없다. **더 좁히려면 AP1302 펌웨어
내부 문서나 벤더 지원이 필요하다** — §5.5 의 "짧은 노출 ISP 폐기 기전 미규명"이 막힌 지점과 같다.

> 근거를 모아 max9296 이슈 [#65](https://github.com/jhw7500/max9296/issues/65) 로 등록했다
> (근인 `ae_on` 비대칭은 [#64](https://github.com/jhw7500/max9296/issues/64), **별개 현상**).
> 드라이버 쪽 당장의 개선 여지: 쌍의 두 채널 `R0x00FC` 가 크게 벌어지거나 한쪽 카운터가 멈춘
> 것을 감지해 **로그만 남겨도** 현장 진단 비용이 크게 준다. 현재는 아무 신호가 없다.

##### 주의 — 판정 도구를 믿지 말 것

프로브의 실시간 동결 판정은 **오탐을 낸다.** IRQ 기준값을 앱 기동 직후에 읽는데 하드 리셋
잔여 인터럽트가 첫 창에서 증분을 만들면 "스트림 시작됨"으로 오인하고, 이후 실제 스트리밍
시작 전 구간이 동결로 잡힌다(실제 사례: `poll_..._slow_t2` 를 동결 @14.68s 로 라벨했으나
원자료는 90 초 CSI 총증분 8, 앱 수신 0 인 **기동실패**였다).
집계는 반드시 `test/classify-freeze.awk` 로 원자료에서 다시 낸다 — 이 분류기는 합성
양성(중간부터 CSI=0)·음성(원본)·기동실패(전구간 CSI=0) 세 경우로 판별력을 검증했다.

**입력 형식이 하나뿐이다.** 헤더가 정확히 `t_us,a_total,a_cnt,b_total,b_cnt,csi_d` 인
회차별 CSV, 즉 `fast_*_t<N>.csv` 와 `poll_*_<arm>_t<N>.csv` 만 받는다. `frz_*`(csi_d 가 3번
필드)와 `frzexp_*`(4번 필드)는 레이아웃이 달라 **쓸 수 없다** — 예전 판은 그런 파일을 먹으면
exit 0 으로 그럴듯한 오답을 냈다. 지금은 헤더를 검사해 `exit 2` 로 거부하고, 데이터 행이
없을 때도 기동실패로 오판하지 않고 거부한다.

```bash
awk -v NAME=poll_slow_t7 -f test/classify-freeze.awk /root/fpsmeas/poll_..._slow_t7.csv
```

#### 5.8.8 재정정 — 근인은 `ae_on` 이 아니라 노출 갈림 (2026-09-08)

**하드웨어 규칙**(운영자 확인): ch0/ch1 은 하나의 CSI 로 SERDES GMSL 링크에 묶여 **같은
`exp_time`** 을 써야 한다. 그래서 런타임 변경도 0x11/0x12 각각이 아니라 **0x3c 로 양 채널에
한 번에** 쓴다. AE 값은 채널별로 써도 된다. `edgeconf_pim.json` 이 이 규칙을 표현한다 —
`exp_time` 은 버스 레벨에만 있고 네 채널 어디에도 없다(`map(has("exp_time"))` 이 전부 false).

**판별 실험** — 4채널 전부 `ae_on=false` 대칭이라 시드 스킵이 양쪽 다 없다(스큐 0). 한 회차
75s 안에서 P1 0~30s 무개입 / P2 30~50s 개입 / P3 50s~ 복귀로 **노출만** 바꾼다. 재기동 없음.

| | 대칭 | 비대칭 |
|---|---|---|
| 주기 미만(`over_period=0`) | 2000/2000 → **117.4** | 2000/**4000** → **46.5** |
| 주기 초과(`over_period=1`) | 11000/11000 → **113.9** (4/4) | 2000/**11000** → **16.1** |

- **절대값도 프레임주기 초과도 무해하다.** 11000us 를 120fps(주기 8,333us)에서 써도 양쪽이
  같으면 정상이다. 드라이버가 찍는 `over_period=1` 경고는 이 고장과 무관하다.
- **용량 반응**: 노출 차 0 → 117.4, 2,000us → 46.5, 9,000us → 16.1 fps.
- **가역**: 되돌리면 재기동 없이 복구된다(109.6 / 114.8).
- `S_sham`(0x12 에 **같은 값** 재쓰기)은 정상 → "개별 주소로 쓰는 행위" 자체가 아니라
  **값이 갈리는 것**이 원인임이 통제된다.

**폐기하는 1차 개정의 주장**

| 폐기 | 반증 |
|---|---|
| "`ae_on` 비대칭이 근인" | `ae_on` 대칭(전부 false)인데 노출만 갈라도 무너진다 |
| "시드 스킵으로 두 시퀀스가 200ms 어긋나는 것이 기전" | `:2938-2952` 의 `msleep(100)` 2회는 고정이고 `max9296_write_exposure()` 는 고정 페이로드다. 시드 2000 과 50000 은 바이트 하나만 다른 **동일 시퀀스**라 스큐가 같은데 결과는 갈렸다 |
| "시드 스킵을 쌍 단위 AND 로 결정하면 고쳐진다" | `ae_on=true` 채널은 시드를 받아도 STEP 2(`:2955`)에서 AE auto 로 돌아가므로 갈림이 남는다 |

**수정 전 v2.12 코드에서 규칙이 깨지던 지점** — dual 에서 0x11/0x12 로 분기하던 5곳:
`:2948`(prepare 시드),
`:3261`·`:3324`(`EXPOSURE_AUTO_CHx` 가 AE off 시 노출도 씀), `:3284`·`:3347`(`EXPOSURE_CHx`).
`:3229`(`V4L2_CID_EXP_TIME`)만 0x3c 로 규칙을 지킨다.

**원인 판별 당시 미확정**: `ae_on` 비대칭이 **명시적 노출 쓰기 없이** AE 수렴값만으로 갈림을 만드는지.
런타임에 `ae_on_ch1` 만 켜 본 1 표본은 정상(118.1fps)이었으나, AE 가 실제로 다른 값으로
수렴했는지 확인하지 못했고 원래 고장 조건(prepare 시점부터 시드 없이 auto)과 시작점이 다르다.

**해결 상태** — max9296 PR #66(`7ec29493eb5019b85a50f874b450bbf9d7b4a1d6`)은 prepare 시드를
쌍 단위로 다시 구성했다. dual 이면 `pair_ae_on`으로 스킵 게이트를 정하고, ch0 캐시를 쌍의
대표 노출값으로 사용하며, 0x3c에 한 번 써서 두 AP1302에 같은 값을 적용한다. AE 모드(0x5002)는
허용된 채널별 값으로 유지한다. 수정 전 10.1/11.3fps였던 `ae_on` 비대칭 갈래는 수정 후
112.3/112.6/111.2/104.7fps로 4/4 정상화됐고, 이슈 #64는 2026-09-08 완료로 닫혔다.

후속 [#67](https://github.com/jhw7500/max9296/issues/67)(채널별 노출 캐시와 하드웨어의 불일치)과
[#68](https://github.com/jhw7500/max9296/issues/68)(철자 기반 정적 계약·CI 공백)도 완료됐다.
간헐 동결 [#65](https://github.com/jhw7500/max9296/issues/65)는 노출 갈림과 별개이며 아직 열려 있다.

수정 전 원자료: 타겟 `/root/fpsmeas/expsplit_20260908_013240.*`(2x2),
`expsplit_20260908_014852.*`(`W_aeon` 포함, 동결 빈발로 절반 무효).

## 6. 드라이버 / 앱 업데이트 후 체크리스트

max9296 v2.12 + HD60 지원 gstApp 을 배포한 뒤 순서대로 수행한다.

1. **버전 확인** — 이월값을 믿지 않는다. 셋 다 같은 값이어야 한다.
   ```bash
   cat /sys/module/max9296/version
   modinfo max9296 | grep ^version
   dmesg | grep -i 'max9296 version' | tail -2
   ```
   (2026-09-07 시점 보드는 **v2.11** 이었다. 메모리에 v2.12 로 잘못 기록돼 있었다.)

2. **열거 확인** — 드라이버가 720p@60 을 실제로 광고하는지. 이게 통과해야 나머지가 의미 있다.
   ```bash
   /root/fpsmeas/run-fps-scenario.sh --res 1280x720 --fps 60 --check-only
   ```
   `1280x720` 과 듀얼와이드 `2560x720` **양쪽**이 60 을 열거해야 두 조합을 다 잴 수 있다.

3. **앱 게이트 확인** — `max9296Prepare.cpp` 의 `kMaxFpsHdFhd`(구판 30). HD 와 FHD 가 분리됐는지
   확인한다. FHD 는 30 을 넘기면 정수 트리거 분주로 오히려 떨어진다는 기록이 있으므로
   HD 만 60 으로 열려야 한다 (이슈 #86).

4. **fps 예산 확인** — 720p 예산은 240 (`max9296Controls.cpp:73`). 2채널 x 60 = 120 통과,
   4채널 x 60 = 240 경계. `dual_enc=TRUE` 면 2배로 계산되어 초과한다.

5. **본 측정**
   ```bash
   /root/fpsmeas/run-fps-scenario.sh --res 1280x720 --fps 60 -k "0+1 0+2" -n 3
   ```

6. **회귀 확인** — 기존 조합이 나빠지지 않았는지 같이 잰다.
   ```bash
   /root/fpsmeas/run-fps-scenario.sh --res 640x360 --fps 120 -k "0+1 0+2" -n 3
   /root/fpsmeas/run-fps-scenario.sh --res 640x360 --fps 30  -k "0+1" -n 2   # 운영 구성
   ```
   §5 기준선과 대조한다.

7. **보고 시 범위를 명시한다** — "하드웨어 한계"가 아니라 "드라이버 vX.YZ 에서, mbus code
   0x2006 기준" 으로 쓴다. 열거는 코드·해상도별로 다를 수 있다.

8. **시험 전에 운영 config 의 카메라 설정을 먼저 읽는다.**
   ```bash
   jq '.VHL_CAM | {cam_width,cam_height,fps,
                   i2c2:{exp_time:.i2c2.exp_time},i2c1:{exp_time:.i2c1.exp_time},
                   ch0:.i2c2.ch0, ch1:.i2c2.ch1, ch2:.i2c1.ch2, ch3:.i2c1.ch3}' \
      /root/shared_v/edgeconf_pim.json
   ```
   버스별·채널별로 **다르게 설정된 항목**(특히 `exp_time`, `ae_on`, `led_flash`, `ae_gain`,
   `hflip`/`vflip`)을 목록으로 뽑고, 각 항목을 **운영값에 맞출지 통제값으로 통일할지 명시적으로
   정한다.** 절반만 통일하면 운영과도 다르고 통제도 안 된 상태가 되어 결과를 오독하게 된다.
   스크립트는 `-x/--exp` 로 노출을 통일하고 되읽어 검증하지만, 나머지 항목은 사람이 확인해야 한다.

## 7. 하드웨어 배치 (참조)

| | ch0 / ch1 | ch2 / ch3 |
|---|---|---|
| max9296 i2c | `2-0048` (`/sys/bus/i2c/devices/2-0048/`) | `1-0048` |
| CSI2 IRQ | `32e50000.csi` | `32e40000.csi` |
| ISI IRQ | `32e02000.isi` | `32e00000.isi` |
| video 노드 | `/dev/video4` | `/dev/video3` |
| subdev | `/dev/v4l-subdev2` | `/dev/v4l-subdev3` |
| prepare 경로 | `max9296Prepare.cpp` `kPreparePaths[0]` | `kPreparePaths[1]` |

`enable` 비트: `1`=left(ch0/ch2), `2`=right(ch1/ch3), `3`=dual-wide(전송 폭 2배).
설정 정본: `/root/shared_v/edgeconf_pim.json` (`chk_cam_operate.sh` 가 `edgeconf_*.json` 중
mtime 최신 1개를 고른다). 채널 키는 `VHL_CAM.i2c2.ch0/ch1`, `VHL_CAM.i2c1.ch2/ch3`.
